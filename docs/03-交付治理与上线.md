# 财税服务协作 SaaS 交付治理与上线 v3.0

---

## 1. 阶段计划与质量门

> 版本：v3.0 
> 交付原则：范围/需求冻结 → 概要/详细设计冻结 → 实现 → 系统集成测试 → UAT → 最终迁移/回滚演练 → 最终测试验收 → 生产就绪评审 → 一次生产上线

### 1.1 计划目的

本文规定全范围从立项到结项的阶段、交付物、确认与放行、变更控制和停止条件。它是阶段准入基线，不以自然日期替代质量证据。

严格瀑布含义：

- 当前阶段的正式基线未经放行，不得作为下一阶段的正式输入。
- 可以在非生产环境开展调研、原型、技术 POC、内部构建、自动化验证和试迁移，但这些活动不能冒充对应阶段完成或对生产客户交付。
- 需求冻结后变更必须走正式 CR；重大变更可要求回退并重新通过受影响质量门。
- 全范围只在一个生产切换窗口整体启用。不得用 MVP、试点 Organization、地区灰度或模块开关隐藏未完成范围。

### 1.2 治理角色与放行模型

本项目由产品所有人主导、AI 编码工具执行交付。治理角色只有以下四类，本节是全部文档中治理角色与放行规则的唯一定义处：

| 角色 | 含义 | 权限与限制 |
|---|---|---|
| `OWNER` | 产品所有人（决策人） | 唯一放行人：需求冻结、变更批准、每道质量门放行、Go/No-Go 均由 OWNER 决定并留书面记录；不得委托 AI 放行 |
| `TAX-ADVISOR` | 财税顾问（外部专业合作方） | 对财税规则口径、会计处理、申报与对账口径出具确认；凡涉及财税正确性的门，缺其确认不得放行，OWNER 不得自我替代 |
| `AI-EXEC` | AI 执行角色（如 Claude Code 等编码代理） | 承担分析、设计、编码、测试、迁移工具等制品生产并附自检报告；不得放行任何门，不得静默改变冻结基线 |
| `MACHINE-CHECK` | 机检 | CI/脚本对可机检条件的客观判定；机检失败即门失败；机检通过不等于放行 |

补充规则：

1. AI 自检报告是证据，不是机检也不是放行；同一门内三者不可互相替代。
2. 法律/合规意见不设常设角色：OWNER 决定是否采购外部合规意见；未取得意见的高风险功能（隐私、电子签、外呼、企业数据、抽成、财税责任）要么阻断，要么由 OWNER 在 本卷《风险与待决策清单》 登记为书面接受的风险。
3. 有真实用户视角需求时（UAT、可用性），可邀请种子代账机构/企业在脱敏或合成数据上试用，其反馈作为证据；放行仍只属于 OWNER。

### 1.4 阶段 0：立项与范围确认

#### 1.4.1 工作内容

- 明确公有云 SaaS 商业目标、基线范围、非范围、成功指标和预算边界；
- 确认 Organization、LegalEntity、Workspace、AccountingBook 四层概念；
- 确认三门户及 audience：平台控制台/PLATFORM、服务机构工作端/PROVIDER、客户企业门户/ENTERPRISE；
- 确认严格瀑布、全范围一次生产上线和变更控制规则；
- 建立风险、决策、供应商调研和文档基线。

#### 1.4.2 `GATE-SCOPE`

必交付：文档手册与产品需求页面卷的范围章节、范围声明、业务案例、预算区间、顶层风险和决策清单。

出口条件：OWNER 放行；没有“销售 Workspace/会计 Workspace”与 Service Workspace 混淆；企业门户进入范围；一次上线原则明确。

### 1.5 阶段 1：需求获取、分析与冻结

#### 1.5.1 工作内容

- 从平台运营、服务机构销售/服务/财务/会计/税务/内部管理及客户企业视角收集需求，可结合种子代账机构访谈；
- 建立功能需求、非功能需求、业务规则、状态、公式、页面范围和验收条件；
- 冻结 Organization capability、participant role、Workspace 生命周期、多 LegalEntity 和持久企业门户；
- 冻结完整范围：CRM、合同、服务、经营财务、会计、税务、内部管理、客户确认、连接器、平台计费、迁移；
- 冻结数据保留、隐私、容量、供应商和迁移外部输入；
- 生成稳定 `BR/FR/NFR/DEC/PAGE/TEST/GATE` ID 和初始追踪。

#### 1.5.2 允许的非生产活动

可制作不可发布的低/高保真原型、规则样例、合成数据演示和供应商能力探针，用于澄清需求；不得将原型或 POC 作为生产承诺，也不得在需求冻结放行前固化不可逆实现。

#### 1.5.3 `GATE-REQ`

必交付：产品需求与页面卷、术语与概念卷、系统设计卷（业务设计部分）和商业计费卷的需求口径，初版风险与待决策清单（本卷），仓库追踪制品初版。

出口条件：

1. 每个需求有稳定 ID、来源、验收条件和优先级/范围归属；
2. 三门户、Organization/Workspace/LegalEntity、参与角色和 PARTNER 待决边界无矛盾；
3. 多合同/服务/续费复用 Workspace，Organization 不按服务方/客户方复制；
4. 财账税公式、职责分离、客户决定和外部 UNKNOWN 规则可测试；
5. 待决事项都有最晚质量门和未决处理；
6. `MACHINE-CHECK` 子条件全部通过，财税口径经 `TAX-ADVISOR` 确认，OWNER 放行。

`GATE-REQ-001～006` 是 `GATE-REQ` 的可机检子条件，不是六个独立阶段门：

| 子条件 | 必须为真的结论 |
|---|---|
| `GATE-REQ-001` | BR/FR/NFR 范围、非范围和优先级无 P0 歧义 |
| `GATE-REQ-002` | Organization、LegalEntity、Workspace、AccountingBook 关系一致 |
| `GATE-REQ-003` | 三 Audience、客户企业门户与 H5 边界冻结 |
| `GATE-REQ-004` | 核心流程、状态、金额、职责分离和欠费传播可验收 |
| `GATE-REQ-005` | 所有 P0 待决事项已有结论、阻断或合法降级 |
| `GATE-REQ-006` | 每条需求已有页面/API/实体/测试的可行追踪路径 |

六项全部通过后，仍由第 1.14 节 `GATE-REQ` 行统一放行；子条件不单独放行，也不得替代父门。未关闭的 P0 需求歧义阻断 GATE-REQ。

### 1.6 阶段 2：概要设计与架构冻结

#### 1.6.1 工作内容

- 系统上下文、三门户部署和 audience 隔离；
- 架构基线冻结的运行组件与可观测性；
- 领域边界、数据所有权、事务、Outbox、分区/分片和容量模型；
- Organization 授权、Workspace grant、连接器适配和人工降级；
- 安全、隐私、审计、灾备和生产拓扑；
- 迁移总体策略、Big-bang 切换与回滚可行性；
- 供应商 POC 方案和一票否决门。

#### 1.6.2 `GATE-HLD`

必交付：系统设计卷（总体架构部分）、架构决策记录、系统/部署/数据流图、容量假设、威胁模型、灾备方案、连接器 POC 计划和迁移概要。

出口条件：AI 自检与设计评审材料齐备，隔离边界、LegalEntity 绑定、连接器授权所有权和一次上线技术路径可实现；关键容量/合规未知项未被伪造成结论；OWNER 放行。

### 1.7 阶段 3：详细设计与契约冻结

#### 1.7.1 工作内容

- 完成系统设计卷与商业计费卷的详细设计，其中商业计费实体、状态、公式、API/事件、测试与迁移规则必须作为详细设计基线冻结；
- 形成页面交互、OpenAPI 契约、事件 Schema、错误码、DDL、约束、索引、分区、状态、公式、权限和审批种子；
- 完成导入导出、后台任务、文件、搜索、报表、审计和客户企业门户设计；
- 完成测试设计、迁移字段映射、对账公式、生产切换/回滚 Runbook；
- 对供应商做非生产 POC；供应商未定能力保留合法人工路径或明确上线阻断。

#### 1.7.2 设计完整性检查

每个范围内需求必须至少映射到业务设计/领域、页面或无 UI 说明、API、实体、状态/公式、权限和测试占位。以下内容不得留给实现阶段自行决定：

- Organization 合并/claim 和跨服务商枚举；
- Workspace 主参与方、subject 变更和多合同复用；
- 三 audience、角色作用域、字段权限和职责分离；
- 合同/账套/申报的 LegalEntity 绑定；
- Organization connector authorization 与 Workspace grant；
- 金额、凭证、税费、确认、申报、缴退税和 UNKNOWN；
- Big-bang 数据映射、对账和回滚；
- 商业计费的 Organization 订阅主体、billing LegalEntity、套餐/价格版本、用量、账单、支付/分配、退款、平台发票、欠费、争议和迁移守恒。

#### 1.7.3 `GATE-LLD`

必交付：系统设计卷与商业计费卷设计版、仓库追踪制品设计版、可机器校验权限种子、可执行 DDL/迁移、OpenAPI/事件 Schema、原型源文件、测试设计和 POC 报告。

出口条件：

1. 需求—设计—页面—API—数据—权限—状态—测试追踪无 P0 悬空；
2. DDL、OpenAPI、事件 Schema、权限种子和状态目录机器校验通过；
3. 计费领域制品与需求、API、迁移、测试及仓库追踪制品同号同义且评审通过；
4. 安全、数据、性能、灾备、迁移、商业计费和连接器自检报告齐备；
5. 外部供应商未完成事项有明确阻断/降级，不宣称中标；
6. 财税规则契约经 `TAX-ADVISOR` 确认，OWNER 放行。

### 1.8 阶段 4：实现与单元验证

#### 1.8.1 工作内容

- 按冻结模块和契约实现全部范围，不改变领域边界；
- 数据库迁移、种子、API、事件、前端三门户、后台任务、文件、审计和监控；
- 单元、组件、数据库约束、契约、静态安全和依赖测试；
- 模拟连接器与已通过 POC 的沙箱适配器；
- 迁移工具、对账工具和部署/回滚自动化；
- 代码评审记录、变更记录和真实制品引用回填仓库追踪制品。

#### 1.8.2 内部构建规则

允许持续集成产生多个内部构建并部署 DEV/TEST；构建号不代表产品版本或生产阶段。发现设计缺陷时提交 CR；`AI-EXEC` 不得以实现便利静默改变 Organization/Workspace、权限、状态、公式或 API。

#### 1.8.3 `GATE-BUILD`

出口条件：

- 全部范围代码完成，编译/静态检查/单元/组件/契约测试通过；
- DDL 可从空库创建并从上一基线升级/回滚；
- OpenAPI/事件/权限种子与设计一致且破坏性变更检测通过；
- P0/P1 代码缺陷清零，代码评审完成；
- 可部署 SIT 包、测试数据、迁移工具和发布说明经 OWNER 放行。

### 1.9 阶段 5：系统集成与非功能测试

#### 1.9.1 工作内容

- 三门户 E2E、跨域流程、状态/公式、权限/审批、文件/消息/搜索/报表；
- Organization、Workspace、LegalEntity 和 PROVIDER 私有数据专项隔离；
- 财务、会计、税务、客户确认、企业 claim 和外部连接器；
- 安全、性能、容量、征期/月末峰值、故障注入、恢复和灾备；
- 第一、第二轮非生产全量试迁移和增量追平技术验证；
- 缺陷修复、全量回归和 UAT 基线封版。

#### 1.9.2 `GATE-SIT`

采用本卷《测试、UAT与验收》的 `GATE-TEST-SIT-EXIT`。P0/P1 为零；安全严重/高危为零；财账税、隔离、性能、恢复和连接器报告通过机检与自检；OWNER 放行。

### 1.10 阶段 6：业务 UAT

#### 1.10.1 工作内容

- 平台运营完整剧本；
- 服务机构客户经营、合同、服务、财务、会计、税务、内部管理完整剧本；
- 客户企业门户持久账号、多个 Workspace、材料、确认、异议、结果、授权和下载；
- 主流程、关键异常、职责分离、法定主体、人工降级和可用性；
- 使用脱敏迁移样本验证业务连续性和培训材料；
- 可邀请种子代账机构/企业在脱敏或合成数据上试用并收集反馈；
- 对 UAT 缺陷修复后执行受影响范围和全量关键回归。

#### 1.10.2 `GATE-UAT`

出口条件采用本卷《测试、UAT与验收》的 `GATE-UAT`：范围内用例全通过，P0/P1 为零，财税与对账口径经 `TAX-ADVISOR` 确认，OWNER 放行。未完成供应商生产资质、正式容量或迁移最终演练不由 UAT 自动放行，继续按后续专项门阻断。

### 1.11 阶段 7：最终迁移、切换与回滚演练

SIT 阶段可进行技术试迁移；只有 UAT 放行后，才以候选生产版本、生产同构拓扑和最终映射进行完整切换演练。

#### 1.11.1 工作内容

- 冻结源范围、最终字段/状态/Organization/Workspace/LegalEntity 映射；
- 执行生产规模全量 + 增量追平；
- 验证停写、最终水位、财账税/文件/权限对账、三门户冒烟和外部动作技术锁；
- 完整执行回滚，验证 post-cutover journal、DNS/流量、队列/回调、旧系统只读/恢复写入和 RTO/RPO；
- 完成培训材料、监控、告警、备份、供应商生产凭证/额度/回调/对账和上线通讯；
- OWNER 审阅所有开放风险。

#### 1.11.2 `GATE-MIG-DR`

仅在 `GATE-UAT` 通过后，以候选生产版本、最终映射、生产规模数据和生产同构拓扑执行。完整回滚、post-cutover journal、外部不可逆动作隔离、旧系统恢复写入以及 RTO/RPO 全部达到本卷《数据迁移、切换与上线》的标准，方可通过；失败不得进入 `GATE-MIG-PROD`。

#### 1.11.3 `GATE-MIG-PROD`

仅在 `GATE-MIG-DR` 通过后执行并关闭。生产规模全量、增量追平、停写/最终水位、切换、三门户冒烟、Organization/Workspace/LegalEntity/Book/权限/文件及财账税和平台计费对账必须全部通过，纳入范围的差异为 0；失败不得进入最终测试验收。

#### 1.11.4 `GATE-TEST-ACCEPT`

仅在 `GATE-MIG-PROD` 通过后，按本卷《测试、UAT与验收》的最终验收口径汇总需求追踪、SIT、UAT、最终迁移/回滚、安全、灾备和缺陷证据。该门通过后方可提交 `GATE-PRR`，本门本身不要求 `GATE-PRR` 已批准。

#### 1.11.5 `GATE-PRR`

必交付：最终迁移/回滚报告、生产 Runbook、Go/No-Go 清单、监控/告警、备份/恢复、供应商生产门、培训/支持安排、值守和回滚决策树。

出口条件：

- `GATE-TEST-ACCEPT` 已通过；其已消费并封存 `GATE-MIG-DR`、`GATE-MIG-PROD` 证据，PRR 不重复改变专项门结论；
- 并行前置 `GATE-CONN-PROD` 已通过；
- 生产凭证、密钥引用、容量、RPO/RTO 和供应商 SLA 证据齐全；
- P0/P1 缺陷和 Stop-ship 风险为零；
- OWNER 放行并确认提交 `GATE-GO-LIVE`。

### 1.12 阶段 8：一次生产上线

#### 1.12.1 上线方式与一次上线的解释

在一个批准的切换窗口执行：停写→最终增量→加载/投影→对账→三门户/隔离冒烟→Go/No-Go→整体开放。旧系统转只读。

外部签署、开票、申报、缴退税可先保持技术锁，待同窗口数据/隔离验证通过后统一解锁；这是已完成版本的安全启动顺序，不是功能分期。

“一次上线”是指范围在同一个生产切换窗口整体启用，不按 MVP、地区、Organization 或模块分批把未完成产品暴露给生产客户。它不禁止：

- 在开发、测试、预生产环境持续集成和内部版本迭代；
- 使用合成数据、沙箱供应商和受控迁移样本开展验证；
- 进行多轮全量试迁移、增量追平和切换演练；
- 在正式切换后对同一已验收版本进行基础设施层面的流量升温、监控和可逆开关控制；
- 对生产缺陷执行经批准的修复和回滚。

任何技术灰度都不能改变功能已完整交付、数据已完整迁移、角色已完整配置的上线前提。

#### 1.12.2 `GATE-GO-LIVE`

通过条件：正式迁移和自动/人工核验通过，三 audience/Organization/Workspace/LegalEntity 隔离通过，财账税对账通过，监控就绪，OWNER 给出 GO。失败则按本卷《数据迁移、切换与上线》的回滚方案执行。

### 1.13 阶段 9：观察、终验与结项

#### 1.13.1 工作内容

- 集中保障、工单、性能、错误率、消息积压、连接器 UNKNOWN、财账税和供应商费用对账；
- 生产缺陷按变更和发布流程修复；

- 形成终验、复盘、遗留风险和文档归档。

#### 1.13.2 `GATE-CLOSE`

### 1.15 变更控制

需求冻结后，任何影响范围、Organization/Workspace 边界、法律主体、账套归属、身份受众、角色权限、金额公式、状态机、外部连接器、计费、数据留存或上线方式的变化，必须提交正式变更请求（CR），由 OWNER 批准。CR 至少包含：变更原因与业务价值；受影响 `BR/FR/NFR/DEC/PAGE/API/ENT/STATE/CALC/TEST/MIG/GATE` ID；合规、安全、成本、进度和一次上线影响；替代方案和不变更后果；数据迁移、兼容与回滚方案；更新后的基线版本和生效门。口头结论不得进入构建。

#### 1.15.1 变更分级

| 级别 | 示例 | 处理 |
|---|---|---|
| C1 基线重大变更 | 范围、Organization/Workspace、三 audience、LegalEntity、金额/税务、上线模式 | 回到 GATE-REQ、GATE-HLD、GATE-LLD 中最早受影响门重审 |
| C2 设计兼容变更 | API 新增可选字段、索引、非语义 UI 调整 | 设计评审、追踪/测试更新后继续 |
| C3 缺陷修正 | 实现偏离已冻结设计 | 缺陷流程、回归和配置审计，不改变需求 |
| C4 紧急生产修复 | P0 事件 | OWNER 应急批准、最小变更、回滚、事后补齐评审和全量回归 |

### 1.16 Stop-ship 条件

以下任一未关闭不得进入一次生产上线：

1. 范围内功能、页面、API、数据或企业门户尚未完成；
2. 三 audience、跨 Organization/Workspace/LegalEntity 隔离失败；
3. Organization claim/错误合并、Workspace 主体变更无安全流程；
4. 财务金额不平、凭证/试算不平、申报/缴退税摘要或 UNKNOWN 不一致；
5. P0/P1 或安全严重/高危缺陷存在；
6. 供应商无合法授权/生产 POC/SLA 且无获准人工路径；
7. 性能、容量、RPO/RTO 未验证；
8. UAT、两轮全量迁移、增量、最终切换/回滚演练未经放行；
9. 生产备份、监控、告警或回滚预案缺失；
10. 仓库追踪制品存在 P0 悬空或伪造制品引用。

## 2. 第三方集成与供应商管理

> 版本：v3.0 
> 原则：只定义能力门、适配契约、供应商治理和 POC；本文不宣布任何候选方中标、签约或具备生产资质

### 2.1 目的与边界

本文规定外部能力如何登记、评估、授权、调用、回调、计量、对账、降级和退出。任何供应商只有同时通过合法授权、技术 POC、安全、商务、SLA、数据处理和生产就绪质量门后，才可成为对应环境和能力的 ACTIVE 供应商。

禁止事项：

- 不以公开宣传页、销售口头承诺或沙箱成功代替书面 SaaS 服务商授权。
- 不使用共享账号、验证码绕过、桌面自动化、非官方接口或抓取作为商业化正式能力。
- 不把模拟连接器、手工登记或测试回调伪装成供应商生产成功。
- 不让 PLATFORM、PROVIDER、ENTERPRISE 三种 audience 读取彼此的密钥、授权正文或越权业务结果。
- 不把 Organization capability、Workspace participant 或菜单可见性当作外部主体授权。

### 2.3 连接器分层模型

#### 2.3.1 固定分层 `BR-CONN-005`

```text
connector_provider
 └─ connector_adapter_version
 └─ connector_credential_version（平台级、按环境、可选）

Organization / LegalEntity / Account
 └─ organization_connector_authorization
 └─ workspace_connector_grant
 └─ connector_request
 ├─ connector_attempt
 └─ connector_event / receipt / usage
```

| 层 | 权威内容 | 不得包含 |
|---|---|---|
| 供应商/适配器 | 能力、环境、制品摘要、Schema、POC、合同和状态 | Organization/Workspace 业务正文、任何明文密钥 |
| 平台凭证版本 | 环境、密钥服务引用、指纹、有效期、轮换链 | Workspace 专属 OAuth/企业授权正文 |
| Organization 授权 | 授权所有者 Organization、外部账号、LegalEntity/账户等主体、同意证据、密钥引用、范围和版本 | 某个 Workspace 的业务许可、平台密钥正文 |
| Workspace grant | Workspace、participant、所用 Organization 授权、能力/动作、业务主体、有效期、额度和版本 | Organization 密钥正文、超出授权范围的动作 |
| 请求与尝试 | 冻结供应商、环境、适配器、平台凭证版本（如适用）、Organization 授权版本、Workspace grant 版本、主体和业务摘要 | 可由客户端覆盖的组织/Workspace 上下文 |
| 事件与回执 | 原始传输密文、验签、路由、规范结果、业务防重键、回执和处理结果 | 未验签即触发的业务迁移 |

#### 2.3.2 授权所有权与 Workspace 使用许可 `BR-CONN-001`

外部账号或主体授权的权威所有者是 Organization，不是 Workspace。每个 `organization_connector_authorization` 必须绑定授权所有者 Organization、能力代码、环境、外部账号命名空间、明确主体类型与本地 ID、同意证据、密钥服务引用、范围、有效期和不可覆盖版本。

典型所有权如下：

- E_TAX、IIT、社保公积金、BANK、客户经营发票和客户企业年度报告通常属于 PRIMARY_CLIENT Organization 的具体 LegalEntity/Account；
- 服务机构 WECOM、CALL、企业数据账户及服务机构自身电子签/开票通常属于 PRIMARY_PROVIDER Organization；
- 具体供应商合同与合法授权可改变上述模式，但必须书面冻结，不能由 Workspace 菜单或发起人身份推断。

Workspace 只能通过 `workspace_connector_grant` 使用一条有效 Organization 授权。grant 必须绑定 Workspace、其 ACTIVE participant、authorization、允许能力/动作、业务主体、有效期、额度和版本，并满足 `grant.scope ⊆ authorization.scope`。创建 grant、创建请求和每次实际外发前均须校验：

1. authorization 所有者与 participant Organization 一致；
2. LegalEntity/Account 属于授权所有者且是当前业务对象的精确主体；
3. Workspace、participant、authorization 与 grant 均 ACTIVE 且在有效期；
4. 动作、环境、额度和数据范围同时被 authorization 与 grant 允许。

更换主服务方或退出 Workspace 时应撤销/结束 grant，不得撤销或改写客户 Organization 自有 authorization；历史请求继续引用冻结的 authorization 与 grant 双版本。Organization 可拥有多个 LegalEntity，合同签署、开票、账套、税务、银行和年度报告必须按对应 LegalEntity 或账户授权，不能仅以 Organization 或 Workspace ID 代替法定主体。

#### 2.3.3 凭证模式 `BR-CONN-002`

| 模式 | 平台凭证 | Organization 授权 + Workspace grant | 允许场景 |
|---|---|---|---|
| `PLATFORM_MANAGED` | 必需 | 视能力必需 | 平台与供应商统一签约、仍需业务主体授权的服务商模式 |
| `PARTICIPANT_MANAGED` | 不得使用 | 必需 | Organization 自有 App、账号、证书或 OAuth |
| `HYBRID` | 必需 | 必需 | 平台 App + 客户/服务机构独立授权 |

任何模式都不得绕过 PRIMARY_CLIENT 对其 LegalEntity、银行、税务、个税、社保和发票主体的 Organization 授权及当前 Workspace grant。服务机构员工不能凭 Workspace PRIMARY_PROVIDER 身份代客户创建授权。

### 2.4 供应商生命周期与选型

#### 2.4.1 生命周期准入门槛

供应商/适配器生命周期的状态集合与迁移条件由系统设计基线权威定义，本卷只登记每一档必须取得的治理证据，不重复状态定义：

- `QUALIFIED` 只表示技术、安全和能力 POC 达标，不表示已签约。
- `CONTRACTED` 只表示合同与法律门已完成，不表示生产配置已验证。
- `ACTIVE` 还必须满足生产凭证、额度、回调、监控、对账、降级和退出演练。
- 同一能力和生产环境首版最多一个 ACTIVE 主供应商；是否建设在线双供应商容灾是范围变更。
- SUSPENDED/RETIRED 阻止新请求，但不得删除历史请求、回调、费用、证据和回执。

#### 2.4.2 候选登记

OWNER 可登记一个或多个候选，但记录必须包含信息来源日期、联系人、公开资料、待书面确认项和状态。本文不列“首选”“备选”或价格结论；候选排名只能来自完成的一致评分表和批准记录。

#### 2.4.3 一票否决门 `GATE-CONN-LEGAL`

以下任一成立即不得进入生产：

1. 无法书面允许本公有云 SaaS 面向独立 Organization/Workspace 提供或展示能力；
2. 关键流程依赖账号共享、验证码绕过、非官方自动化或未授权抓取；
3. 无法按 Organization、Workspace、LegalEntity/账户隔离密钥、请求、回调、数据和费用；
4. 无沙箱、无稳定查单、无幂等/回调机制，或 UNKNOWN 无法恢复；
5. 无安全、隐私、数据留存、数据导出/删除、分包商和合同退出条款；
6. 无生产 SLA、故障升级渠道或费用无法对账；
7. 无法提供关键法律/财税动作所需的结果回执或证据链。

### 2.5 POC 总体规则

#### 2.5.1 POC 入门条件 `GATE-CONN-POC-ENTRY`

- 能力范围、样本、成功/失败标准、环境和数据类型已批准；
- 仅使用合成或经授权脱敏数据；
- 候选提供官方文档、沙箱、限流、错误码和技术支持渠道；
- OWNER 已确认 POC 不构成生产或采购承诺（外部合规意见如取得则一并归档）；
- POC 制品、日志、密钥和数据有清理责任人。

### 2.7 请求、回调、幂等与错误

#### 2.7.1 出站请求 `BR-CONN-003`

首次尝试必须冻结供应商、环境、适配器制品、平台凭证版本（如适用）、Organization authorization 及配置版本、Workspace grant 版本、participant、Organization、LegalEntity/账户主体、业务对象版本和内容摘要。每次技术尝试只追加 attemptNo、实际版本、时间、请求/响应摘要、规范结果、供应商错误、费用和关联查单。

请求状态遵循系统设计基线定义的连接器请求状态机。技术重试沿同一逻辑请求；业务修正建立后继请求并引用原请求。`UNKNOWN` 不得直接重提、重复申报或重复扣款。

#### 2.7.2 回调顺序 `BR-CONN-004`

```text
入口环境冻结与限流
→ 原始传输密文持久化与传输指纹防重
→ 选择对应环境平台凭证、Organization authorization、Workspace grant 及保留适配器版本
→ 验签、时间窗和来源校验
→ 确认外部账号命名空间、Organization/Workspace/主体路由
→ 可靠事件号或规范业务摘要防重
→ 校验业务对象允许迁移
→ 异步处理、审计和回执归档
```

验签失败、跨环境、无法路由、主体不匹配或伪造事件进入 QUARANTINED。平台运维只能受控重新验签/路由或忽略，不能直接标记业务成功。

#### 2.7.3 错误映射

供应商原始错误只保存脱敏摘要和加密原文引用；前端使用稳定平台错误类别：配置、授权、主体不匹配、限流、暂时故障、明确拒绝、结果未知、签名、回调隔离和费用差异。供应商 HTTP 200 不等于业务成功，HTTP 超时也不等于失败。

### 2.8 人工路径与降级

当合法正式接口不可用时，允许人工导入、导出、办理和回执登记，但必须：

1. 使用同一业务状态、Organization 授权证明、Workspace 使用许可、权限、职责分离、二次确认和内容摘要；
2. 保存实际办理人、Organization/Workspace/LegalEntity、办理时间、来源和扫描通过回执；
3. 禁止填写虚假外部请求号、供应商事件或 UNKNOWN；
4. 人工成功必须是明确可验证结果，不能用“已提交”替代“已受理/已缴”；
5. 自动与人工路线的状态和审计可统一查询、不可重复执行。

### 2.9 生产启用与变更门

#### 2.9.1 生产启用 `GATE-CONN-PROD`

必须同时满足：

- `GATE-CONN-LEGAL`、`GATE-CONN-POC-EXIT`、安全和采购合同完成；
- 生产适配器制品、Schema、凭证和回调均版本化，健康检查通过；

- 监控、告警、查单、隔离队列、人工降级和供应商升级联系人到位；

#### 2.9.2 升级、轮换和更换

ACTIVE 适配器版本不得原位覆盖。升级/回退先暂停新流量、在非生产重跑 POC/契约回归、创建新版本、生产健康检查后原子切换。旧版本保留至全部在途请求、查单、回调宽限、审计和法定留存结束。

### 2.10 用量、费用与对账

```text
平台计量数量 = Σ合格 connector_usage
供应商账单差异 = 供应商计费数量/金额 - 平台匹配数量/金额
```

## 3. 数据迁移、切换与上线

> 版本：v3.0 
> 上线模式：合同全范围 Big-bang 一次生产切换；允许多轮非生产试迁移和可验证回滚演练

### 3.1 目标与原则

本文规定从现有 CRM、代账、税务、平台商业计费、文件和辅助系统迁入统一 Organization/Workspace 模型的盘点、映射、试迁移、增量追平、正式切换、验证和回滚方法。

强制原则：

1. **一次生产上线。** 生产切换窗口内整体启用已验收范围，不按模块、地区、Organization 或 Workspace 把未完成能力逐步暴露给生产用户。
2. **非生产可多轮迭代。** 开发、测试、UAT、预生产可反复构建、全量迁移、增量追平和回滚演练。
3. **源数据先获授权。** 数据所有权、导出权、个人信息处理、第三方证据可迁移性和法定留存未确认时不得迁移。
4. **先对账后切换。** 迁移工具成功不等于业务验收；财务、账务、税务、文件和参与关系均须独立对账。
5. **历史不可伪造。** 缺失审批、回调、签署证据或操作日志时标记来源与限制，不生成虚假系统事件。
6. **Organization 不按身份复制。** 同一实体不因在不同 Workspace 扮演不同角色而建立“服务方表/客户表”副本；角色由 participant 表达。
7. **Workspace 不按合同复制。** 一个稳定服务关系下的多合同、服务项目和续费周期聚合到同一 Workspace；迁移规则不得“一合同一 Workspace”。
8. **可回滚不等于可忽略外部动作。** 正式对外签署、开票、申报、缴款等一旦发生，回滚须先对账并处理外部结果，禁止简单恢复数据库造成重复动作。

| Organization/IAM | Organization、LegalEntity、成员、员工、部门、岗位、角色授权、邀请 | 密码不迁明文；无可验证身份时发新邀请 |
| Workspace | Workspace、participant、membership、关系时间线、发布投影 | PARTNER 生产启用未冻结时仅迁记录并禁用登录/动作 |

| 合同/财务 | 合同及版本、服务项、收款计划、回款/核销、销售发票、退款、成本、客户资金账户 | 金额需逐合同和总账双重对账 |

#### 3.2.1 平台商业计费迁移 `MIG-BILL-001～006`

| `MIG-BILL-002` | 旧套餐、权益、价格、额度、优惠和欠费规则转换为带生效区间的不可覆盖版本；无法证明版本的历史保留来源和置信度，不补造批准。 |

| `MIG-BILL-004` | 账单、账单行、支付、分配、退款/冲正和平台发票按来源主键与业务引用逐笔迁移和对账；平台账与 FIN 经营财务、ACC 法定账套分别迁移，禁止净额混写。 |
| `MIG-BILL-005` | 历史欠费限制迁为 subscription 状态历史及其策略版本、触发原因和生效时间；不得回写 Organization、Workspace、participant、membership 或 AccountingBook 的业务状态。 |
| `MIG-BILL-006` | 迁移前后按 Organization、billing LegalEntity、币种、期间、状态和金额逐维守恒；明细差异必须为 0，不得用跨主体、跨期间或汇总净额抵销。 |

### 3.3 源系统盘点 `MIG-PLN-001`

每个源必须形成经 OWNER 确认的清单：

| 类别 | 必填内容 |
|---|---|
| 责任 | 数据来源方、导出执行方（AI-EXEC 或来源系统方）、财账税口径确认方（TAX-ADVISOR） |
| 技术 | 系统/版本、数据库/API/文件、字符集、时区、主键、增量水位、附件目录 |
| 法律 | 所有权、导出权、个人信息、第三方合同、留存、删除和跨境情况 |
| 容量 | 各实体行数、年度、附件数/字节、最大文件、每日增量和峰值；套餐/订阅/用量/账单/支付/退款/平台发票及状态历史逐类数量 |
| 质量 | 缺失、重复、非法状态、孤儿、金额差、计费守恒差、试算差、UNKNOWN、无主文件 |
| 范围 | 全量迁移、只读留存、不迁、人工补证、匿名化和销毁 |
| 时间 | 历史冻结点、全量提取、增量追平、停写、切换和回滚窗口 |

源清单未经 OWNER 确认不得进入正式映射评审。

### 3.4 核心映射规则

#### 3.4.1 Organization 与 LegalEntity `MIG-ORG-001`

1. 旧“租户公司”显式映射为具备 `PROVIDE_SERVICE` capability 的 Organization，并将旧平台订阅归属迁移/引用为该 Organization 的订阅主体；旧“客户公司”映射为 Organization、LegalEntity 和 PROVIDER 私有客户经营关系，而不是第二类客户实体。不得机械把全部 `tenant_id` 改名为 `organization_id`。
2. Organization 可拥有多个 LegalEntity。法定名称、USCC、证件、地区、有效期和来源证据分别进入 LegalEntity 版本。
3. 合同、开票、AccountingBook、税务登记、申报、缴退税和银行账户必须映射到具体 LegalEntity；只映射到 Organization/Workspace 视为阻断。
4. 源数据同一企业存在多个客户记录时，先进入候选匹配，不得仅按名称自动合并。USCC、历史来源、联系人、合同主体和人工核验共同决定。
5. 跨服务机构不得通过 USCC、名称或手机号枚举另一服务商是否已有 Organization。匹配服务只返回不泄露存在性的受控 `claim_required/conflict` 结果，并由独立核验流程处置。
6. 错误合并必须可回退：合并前冻结双方对象、引用数量、LegalEntity、Workspace、合同、账套和税务影响；财账税事实已混合时禁止自动拆分。
7. 错误认领/claim、同一企业多 Organization、同一 USCC 归属冲突必须形成异常清单和批准结论，不由迁移脚本任选其一。

#### 3.4.2 Workspace `MIG-WSP-001`

迁移分组键必须表达稳定服务关系，候选维度至少包括主服务 Organization、主客户 Organization、服务隔离要求和历史关系连续性；合同号、续费号或单个服务项目不能单独成为 Workspace 唯一键。

每个拟激活 Workspace 必须：

- 恰有一个 ACTIVE `PRIMARY_PROVIDER` 和一个 ACTIVE `PRIMARY_CLIENT`；
- 双方 Organization 均为 ACTIVE，每个拟激活 `workspace_subject` 对应的客户 LegalEntity 也必须为 ACTIVE 且与业务匹配；
- 每个 ACTIVE `workspace_subject.client_claim_id` 必须引用 PRIMARY_CLIENT Organization 对目标 LegalEntity 的有效期内 ACTIVE `CONTROL` claim；若采用 `REPRESENTATION`，必须有经批准的 owner mapping/代表关系证据。`CONTROL` 的 Organization 必须与 `legal_entity.owner_organization_id` 一致，且两类 client claim 均须覆盖目标 LegalEntity 和拟激活有效期；
- PRIMARY_PROVIDER Organization 必须另以覆盖同一 Workspace、目标 LegalEntity、服务范围和拟激活有效期的有效合同，或有效期内 ACTIVE `SERVICE_AUTHORIZATION`，证明服务权；迁移写入并冻结 `workspace_subject.provider_service_evidence_type=CONTRACT/SERVICE_AUTHORIZATION` 及对应 evidence ID/version/hash/有效期，合同路径另保留签署/生效证据。该“合同或授权”规则只判定 Workspace 服务关系；税局、银行、电子签等受监管具体动作仍须按对应领域/连接器规则另验专用 authorization/grant。`SERVICE_AUTHORIZATION` 只证明服务权，绝不能写入或替代 `workspace_subject.client_claim_id`；
- 上述 client claim、provider 服务权证据与企业用户取得 Organization 管理权/成员权限的证据使用独立记录、证据、审批、版本和有效期，任何一项均不得由另一项推导；
- 多合同、服务项目、续费周期按来源保留并指向该 Workspace；
- 服务机构私有 CRM、成本、绩效、内部审批意见不写入对客发布投影；
- 客户企业门户只生成其 Organization 可见的 Workspace membership 和发布内容。

无法同时补齐上述 PRIMARY_CLIENT `CONTROL`/经批准 `REPRESENTATION` owner mapping 证据与 PRIMARY_PROVIDER 服务权证据（有效合同或 ACTIVE `SERVICE_AUTHORIZATION`），或任一证据失效、范围不匹配、来源冲突未解决的候选 Workspace，只能保持 DRAFT 或进入 SUSPENDED 阻断队列，不得迁移为 ACTIVE；provider 的合同或 `SERVICE_AUTHORIZATION` 均不得补位 client claim，企业用户管理权仍须另行邀请、验证和批准。

Workspace 主服务方、主客户方或关键 LegalEntity 发生变更时，必须先执行 subject 影响评估，覆盖合同、账套、申报、连接器、授权、成员、材料、外部回调和留存。无法证明连续合法关系时新建 Workspace，不得静默换主体。

#### 3.4.3 身份、成员与门户 `MIG-IAM-001`

- 统一登录身份按已验证登录标识匹配；同名不得自动合并。
- 旧服务机构员工建立 Organization membership，再按职责建立 Workspace membership/role assignment。
- 旧客户联系人只迁联系人关系，不自动成为 ACTIVE 企业门户成员。系统发送新邀请，验证目标联系方式、Organization 和 Workspace 后才激活。
- PLATFORM/PROVIDER/ENTERPRISE audience 不从旧角色名推断，必须按目标入口、Organization membership 和参与关系显式生成。
- 密码、MFA 秘密、刷新令牌和第三方密钥不通过明文迁移；无法安全导入时强制重置/重新授权。

#### 3.4.4 业务编号和状态 `MIG-BIZ-001`

目标内部 UUID 新建，保留 `source_system/source_key/source_version` 唯一映射。旧业务编号作为不可变来源编号；新编号按目标规则分配且不得复用。状态映射表必须逐状态定义目标、补证要求和失败策略，未知或非法状态进入异常队列，禁止默认为成功/完成。

#### 3.4.5 财务、会计与税务 `MIG-FAT-001`

- 合同金额、收款计划、确认回款、核销、退款、销售开票分别对账；经营财务不得直接生成客户法定凭证。
- 每个 AccountingBook 仅以 `owner_legal_entity_id` 作为唯一永久归属键；owner Organization 必须由该 LegalEntity 的 `owner_organization_id` 派生并校验，不能作为第二归属键独立迁移、独立改写或与 LegalEntity 产生不一致。不以 Workspace 作为所有者，也不因服务关系变化改写归属；科目、期初、凭证、账簿、报表和档案保持同账套/期间链。
- 迁移时按当前服务关系新建或复用 `workspace_book_assignment`，显式关联 Workspace、AccountingBook、服务项目/服务类型和有效期。assignment 结束、续接或更换 PRIMARY_PROVIDER 只追加/结束服务关联，不复制 AccountingBook，也不改写账套 `owner_legal_entity_id`、由其派生的 owner Organization 或历史事实。
- 凭证借贷不平、期初试算不平、同期间多个当前版本、已结账后普通变更为阻断。
- 税务登记、义务、测算、确认、申报、缴退税和回执必须同 LegalEntity、期间、税种和版本；UNKNOWN 不能映射为失败或成功。
- 缺少扫描回执的历史申报/缴款可以标记 `HISTORICAL_UNVERIFIED` 并限制动作，但不得伪造已验签连接器事件。

#### 3.4.6 文件与连接器 `MIG-FILE-001`

文件迁移前计算大小、MIME、SHA-256、敏感级别、来源和业务关系；上传后复算摘要并执行安全扫描。失败文件进入隔离区且不绑定为有效证据。

连接器迁移必须先确定 `organization_connector_authorization.owner_organization_id`，授权所有者永远是 Organization；再按连接器 capability 将 `authorized_subject` 明确为 `LEGAL_ENTITY` 或 `CONTROLLED_ACCOUNT`，并为获准使用的 Workspace/participant 建立 `workspace_connector_grant`。税局、银行能力强制绑定具体 LegalEntity；其他能力仅在适配器契约和批准证据要求时绑定 LegalEntity，否则可绑定受控外部账号，不得用 Workspace 取代授权所有权。税局、银行等客户主体授权不得转归服务机构；企微、外呼等服务机构自有授权不得转归客户。更换服务机构只结束 grant，不改写原授权历史。只迁密钥服务引用或执行重新授权；沙箱凭证、共享账号和来源不明令牌一律不迁生产。

### 3.5 迁移任务状态 `STATE-MIG-001`

```text
DISCOVERED → MAPPED → EXTRACTED → STAGED → VALIDATED → LOADED → RECONCILED → ACCEPTED
 ↘ REJECTED/QUARANTINED/FAILED
```

| 状态 | 强制证据 |
|---|---|
| DISCOVERED | 源清单、责任人、授权和范围 |
| MAPPED | 字段/字典/状态/主体/敏感级别映射经机检与 OWNER 确认 |
| EXTRACTED | 提取水位、数量、文件清单、摘要 |
| STAGED | 暂存隔离、解析结果、恶意文件检查 |
| VALIDATED | 字段、关系、状态、权限和业务规则报告 |
| LOADED | 目标批次、逐行结果、幂等键和版本 |
| RECONCILED | 数量、金额、试算、税务、文件和抽样对账 |
| ACCEPTED | 对账机检通过、财账税口径经 TAX-ADVISOR 确认、OWNER 放行 |

同一根迁移任务的 `source_system + source_key + source_version` 必须幂等。PARTIAL 成功只允许重跑未成功项，不得重复成功对象或外部动作。

### 3.6 对账规则

#### 3.6.1 数量与关系 `MIG-REC-001`

至少对账：Organization、LegalEntity、Workspace、三类 participant、成员、联系人、合同/版本、服务项目、续费、账套、期间、申报义务、文件和来源映射；平台计费还须逐类对账套餐/版本/权益、价格/欠费策略版本、订阅/变更、billing profile、meter、usage、revenue base、账单/行、支付/分配、退款/冲正、平台发票、争议/对账和状态历史。一般目标数量差必须能由合并、拆分、排除、失败或新增规则逐项解释；`MIG-BILL-001～006` 纳入迁移基线后的逐类数量差必须为 0。

#### 3.6.2 金额 `MIG-REC-002`

```text
合同差额 = Σ源有效合同应收 - Σ目标有效合同应收
回款差额 = Σ源已确认回款 - Σ目标已确认回款
核销差额 = Σ源有效核销 - Σ目标有效核销
开票差额 = Σ源有效销售发票 - Σ目标有效销售发票
退款差额 = Σ源已完成退款 - Σ目标已完成退款
账户余额差 = 源流水重算余额 - 目标流水重算余额
平台账单应付差额 = Σ源有效账单应付 - Σ目标有效账单应付
平台支付实收差额 = Σ源已确认平台支付 - Σ目标已确认平台支付
平台支付分配差额 = Σ源有效分配 - Σ目标有效分配
平台退款/冲正差额 = Σ源已完成平台退款与冲正 - Σ目标已完成平台退款与冲正
平台发票有效金额差额 = Σ源有效平台发票 - Σ目标有效平台发票
```

上述经营财务和平台计费金额差额必须分别为 0；经批准不迁项须在源基线和排除清单中同时体现，并从双方可迁移基线隔离，不能留下非零差额或用目标调整行掩盖。

#### 3.6.3 会计与税务 `MIG-REC-003`

- 各账套期初、累计借贷发生、期末余额和试算一致；抽样凭证逐行一致。
- 已结账期间数量、版本、报表摘要和档案清单一致。
- 各 LegalEntity、税种、期间的申报状态、申报号、应缴/实缴/退税和回执摘要一致。
- UNKNOWN、拒绝、更正、作废和历史未核验项单独列示，不可净额抵销。

#### 3.6.4 文件 `MIG-REC-004`

```text
文件完整率 = 摘要一致且扫描通过的已绑定文件数 / 应迁文件数
```

关键合同、签署证据、凭证附件、申报/缴款回执和档案清单要求 100%；非关键文件阈值由 OWNER 在 GATE-REQ 冻结（外部合规意见如取得则一并归档）。

#### 3.6.5 平台计费守恒与状态历史 `MIG-BILL-005`、`MIG-BILL-006`

平台计费必须在 Organization、billing LegalEntity、币种、期间和状态的交叉维度同时满足：

```text
用量数量差 = Σ源可迁 usage quantity - Σ目标同 meter/version/watermark usage quantity = 0
账单数量差 = 源有效账单及行数 - 目标有效账单及行数 = 0
支付/分配数量差 = 源支付及分配数 - 目标支付及分配数 = 0
退款/平台发票数量差 = 源有效退款/发票数 - 目标有效退款/发票数 = 0
状态历史差 = 源有效状态迁移节点数 - 目标状态历史节点数 = 0
```

- subscription、bill、payment、refund、platform invoice 和 dispute/reconciliation 的状态历史须保留来源键、from/to、策略/规则版本、effective_at、原因和证据摘要；不得只迁最终状态。
- 每个目标当前状态必须能由迁入的有序状态历史重放得到；非法跳转、缺节点、重复终态或 UNKNOWN 被改写为成功均为阻断。
- `MIG-BILL-005` 只恢复 subscription 限制历史，不改变 Organization/Workspace/participant/membership/AccountingBook 状态。
- `MIG-BILL-006` 的数量、金额和状态历史差异全部为 0 后才可放行；不得以总额相等掩盖明细、主体、币种、期间或状态差异。

### 3.7 迁移轮次

| 轮次 | 环境 | 目标 | 出口 |
|---|---|---|---|
| 样本迁移 | 测试 | 验证字段、状态、Organization/Workspace 分组 | 映射评审通过 |
| 全量试迁移 1 | 测试 | 暴露质量、容量、性能和异常 | 问题分类及修正规则经 OWNER 确认 |
| 全量试迁移 2 | UAT | 用脱敏样本验证修正、全域对账、平台计费守恒和门户可见性 | 财账税、计费、状态历史及隔离差异为 0 并经 TAX-ADVISOR 确认、OWNER 放行 |
| 增量追平演练 | UAT | 验证水位、幂等、删除/更正、计费用量与在途状态 | 纳入基线的增量及计费差异为 0 |
| 最终完整回滚演练 | 预生产 | `GATE-UAT` 后以候选生产版本、最终映射、生产规模数据和生产同构拓扑执行完整回滚、post-cutover journal、外部动作隔离、旧系统恢复写入及 RTO/RPO | `GATE-MIG-DR` 通过；失败不得进入最终切换演练 |
| 最终全量/增量、停写、切换与对账演练 | 预生产 | `GATE-MIG-DR` 后以同一候选生产版本执行生产规模全量、增量追平、停写/最终水位、切换、三门户冒烟以及财账税/计费/权限/文件对账 | `GATE-MIG-PROD` 通过且纳入范围差异为 0 |
| 正式迁移 | 生产 | Big-bang 切换 | `GATE-GO-LIVE` 批准并执行 |

至少两次全量试迁移、一次增量追平和一次完整切换/回滚演练通过，方可进入生产就绪评审。

### 3.8 正式切换时间线

具体时刻由 OWNER 冻结，逻辑顺序不可颠倒：

| 相对时间 | 动作 | 责任 |
|---|---|---|
| T-30 天 | 冻结源范围、映射、清洗责任和停写窗口 | OWNER |
| T-14 天 | 完成预生产全量演练、性能和回滚演练 | 实施、研发、测试、运维 |
| T-7 天 | 发布培训、支持、权限、生产供应商和应急清单 | 产品、运营、安全 |
| T-48 小时 | 变更冻结；确认备份、容量、监控、工单和联系人 | 上线经理 |
| T-0 | 源系统停写并记录最终水位；业务进入冻结窗口 | 源系统负责人 |
| T+ | 最终增量提取、校验、加载、索引/投影重建 | 数据迁移负责人 |
| T+ | 自动对账与财账税/文件/权限人工核验 | 数据、会计、税务、安全 |
| T+ | 三门户冒烟、跨 Organization/Workspace 隔离和关键流程验证 | 测试、业务代表 |
| T+ | Go/No-Go 决定 | OWNER |
| Go | 同一版本整体开放；旧系统保持只读 | 运维、业务 |
| Go 后观察 | 监控、对账、工单、外部请求和回滚窗口管理 | 联合保障组 |

外部签署、开票、申报、缴退税等不可逆动作可在同一生产切换窗口内先保持技术锁，待数据/隔离冒烟通过后统一解锁；这属于同一完整版本的安全启动顺序，不是功能分期或隐藏未完成范围。

### 3.9 上线验证 `MIG-VAL-001`

上线前后至少验证：

1. PLATFORM/PROVIDER/ENTERPRISE audience 互斥；
2. 两个服务机构无法通过 USCC、名称、搜索、导出或对象键枚举对方 Organization；
3. 同一 Organization 的多个 Workspace 相互隔离，企业门户只见本 Organization 参与关系；
4. 错误 Organization 合并/claim 和同企业多 Organization 冲突保持阻断，不被脚本静默处理；
5. PROVIDER 私有线索、备注、成本、绩效、内部审批不进入客户企业门户；
6. 每个 ACTIVE Workspace 恰一 PRIMARY_PROVIDER 和一 PRIMARY_CLIENT；
7. 多合同、服务、续费复用稳定 Workspace；
8. 每个合同、账套、申报和缴退税绑定具体 LegalEntity；
9. 财务金额、凭证试算、申报状态和文件摘要对账通过；
10. 企业 claim、邀请、成员、角色和下载均按目标 Organization/Workspace 生效；
11. 连接器授权主体、回调路由、UNKNOWN 查单和幂等正确；
12. 平台订阅、用量和账单与服务机构经营财务/客户法定账套分开。

### 3.10 回滚方案

#### 3.10.1 回滚触发 `MIG-RBK-001`

任一条件成立即暂停新写入和外部动作，提交 OWNER 决定：

- Organization/Workspace/三门户隔离出现可利用的数据泄露；
- 合同、回款、账户、凭证、试算、申报或缴退税存在不可解释的重大差异；
- 身份、权限或企业 claim 大面积错误；
- 关键文件/回执摘要损坏或无法读取；
- 重复签署、开票、申报、扣款风险无法阻断；
- 核心系统持续不可用且预计超过批准 RTO；
- 迁移结果无法在批准窗口内完成对账。

#### 3.10.2 回滚准备

- T-0 前完成源数据库、文件、配置、密钥引用和最终水位不可变备份；旧系统切换后只读。
- 新系统从开放起记录完整 post-cutover journal，包含每个写命令、业务版本、外部请求和结果。
- 演练并批准可反向导入的对象白名单；财务、税务和外部动作不在无证据自动反向范围。
- 明确回滚窗口、决策人、停写通知、DNS/流量、会话撤销、队列隔离和连接器暂停步骤。

#### 3.10.3 回滚执行 `MIG-RBK-002`

```text
停止三门户新写与外部动作
→ 隔离队列和回调但继续安全接收原始事件
→ 冻结 post-cutover journal 和最终新系统水位
→ 核对已发生外部/资金/财税动作
→ 恢复旧系统至 T-0 并重放已批准可逆增量
→ 对不可逆动作逐笔人工对账/补录
→ 验证权限、金额、状态和文件
→ OWNER 批准旧系统恢复写入
```

若已经发生无法安全回灌的申报、缴款、签署或开票，禁止机械回滚；应保持新系统只读证据、隔离受影响范围并执行经批准的前向修复或业务连续性方案。

### 3.11 数据保护与清理

迁移暂存区、导出包和对账报告按敏感级别加密、限时授权、完整审计。非生产只使用合成或经批准脱敏数据。迁移完成后按批准期限销毁临时明文和多余副本；源系统只读留存、归档或销毁须满足合同、隐私、会计、税务和审计最长保留期。

### 5.7 风险升级与决策关闭

#### 5.7.1 升级规则

- H/H 风险每周向项目委员会报告；触发时立即报告并评估 Stop-ship。
- 临近最晚门仍无证据的决策自动升级为该质量门阻断项。
- 供应商、法务、税务、迁移源和真实容量等外部输入不能由项目团队“合理假设”关闭。
- ACCEPTED 风险必须记录接受人、剩余影响、期限、监控和应急；隔离、资金、会计平衡、税务重复提交和不可恢复数据损坏原则上不可接受。

#### 5.7.2 风险与决策执行记录最小字段

摘要表之外必须逐项建立可审计执行记录；共同必填字段为：`record_id`、`item_id`、`accountable_owner_user_id`、`accountable_owner_name`、`accountable_owner_role`、`status`、`latest_gate`、`evidence_refs`、`closure_evidence_refs`、`closure_conclusion`、`approved_by`、`closed_by`、`closed_at`、`updated_at`。同一时点只允许一个实名 accountable owner；转交时保留前后 owner、原因和时间线。

风险接受还必须记录剩余概率/影响、接受期限、监控指标、触发器、应急和复审门。决策关闭还必须记录结论、备选方案、理由、受影响 ID、数据/迁移/API/权限/测试影响、成本/工期、回滚和 `supersededBy`。APPROVED 后改变语义必须发起新决策或 CR，不覆盖旧记录。

#### 5.7.3 重叠主题的权威与依赖边界

| 主题 | 权威决策 | 依赖决策及禁止事项 |
|---|---|---|
| 企业门户功能与商业收费 | `DEC-BILL-001` 权威决定基础权益、增值收费和商业条款 | `DEC-ENTP-003` 只决定功能基线、页面呈现和 entitlement 消费；不得另定收费项、价格或合同条款 |
| 生产回滚与迁移回灌 | `DEC-MIG-004` 权威决定最终停写/切换/回滚窗口；`DEC-MIG-005` 权威决定 post-cutover journal 与可回灌白名单；两项最晚在 `GATE-MIG-DR` 前冻结 | `DEC-OPS-002` 只决定同窗口发布/技术锁，`DEC-OPS-003` 只决定基础设施执行机制并消费两项 MIG 结论；均不得改变窗口或扩大回灌范围，`GATE-PRR` 只核验已批准版本与演练证据，不首次决策 |

依赖决策的执行记录必须引用权威决策 `record_id` 与已批准版本；权威结论变化时，依赖项自动重开并重新经过受影响质量门。

### 5.9 当前总体结论

当前为文档重构基线，所有风险与决策仍需在对应门前取得真实证据。尤其不得提前宣称：供应商已中标、PARTNER 已开放、企业 claim 已合法、容量已验证、税务规则已覆盖、迁移可回滚或生产上线日期已确定。
